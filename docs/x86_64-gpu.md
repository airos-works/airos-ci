# x86_64 GPU: NVIDIA driver, NVDEC, NVK and Zink

This is the X399 workstation's graphics stack: a GTX 1080 Ti (Pascal). It
also runs on a GTX 1070. The details are in Haiku's
`docs/x399-workstation/STATUS.md`. The stack has four parts. Each one now
comes from Git:

| Part | What it does | Source |
|---|---|---|
| `nvidia_rm`, `nvidia_rm_modeset` | kernel driver: X547's Haiku OS layer around NVIDIA's resource manager, plus NVKMS for display | haiku `src/add-ons/kernel/drivers/graphics/nvidia_rm` (from X547/nvidia-haiku, forked as jmgasper/nvidia-haiku `airos`); jmgasper/open-gpu-kernel-modules `airos-570.86.16-haiku` (X547's Haiku branch); the RM core `nv-kernel.o_binary` of NVIDIA's 570.86.16 Linux driver, downloaded from NVIDIA and checked against its SHA-256 |
| `nvidia_rm.accelerant` | app_server's side: modes, displays, the cursor, vertical sync | haiku `src/add-ons/accelerants/nvidia_rm` |
| `nvdec` media add-on | H.264 (and H.265 for programs that ask) decoded on the card's NVDEC engine | haiku `src/add-ons/media/plugins/nvdec`, with the RM API of jmgasper/mesa-nvk |
| NVK | Vulkan on the card | jmgasper/mesa-nvk `airos-nvk-r2`: X547/mesa `mesa-nvk-r2` (`b28d7c6`) plus haiku `docs/x399-workstation/patches/mesa-nvk/0001-0007` |
| Zink renderer add-on | Haiku's OpenGL kit (BGLView programs) on Vulkan | jmgasper/mesa `airos-22.0.5-hgl`: Mesa 22.0.5, HaikuPorts' Haiku patches, and haiku `docs/x399-workstation/patches/mesa-hgl/0001-0014` |

## In the x86_64 image

The sdk-deps workflow cross-builds all of it on the build server:

- `deps/build-nvidia.sh`: the driver, the accelerant and NVDEC, from the
  Haiku tree of the x86_64 SDK. Jam does not build them, so every x86_64
  image build runs this too (about 20 seconds when little changed). A change
  to `nvidia_rm` or NVDEC in Haiku's master reaches the next image like any
  other change.
- `deps/build-nvk.sh`: NVK. Its shader compiler, NAK, is written in Rust.
  `sdk/build-rust.sh` installs a pinned nightly (2026-09-15) and builds std
  for `x86_64-unknown-haiku`, a tier 3 target with no prebuilt std, using
  cargo's `-Zbuild-std`; the result is a rustc `--sysroot`. It also installs
  bindgen and cbindgen. Mesa's host compilers (`mesa_clc`, `vtn_bindgen2`)
  are built from the same tree with Ubuntu's LLVM 18.
- `deps/build-zink.sh`: the Zink renderer add-on (Mesa 22.0.5, against
  HaikuPorts' Vulkan loader).

Where they go in the image:

| Part | Path |
|---|---|
| driver, accelerant, NVDEC | `system/non-packaged/add-ons` |
| `libvulkan_nouveau.so` | `system/non-packaged/lib` |
| NVK's manifest | `system/non-packaged/add-ons/vulkan/icd.d`, where HaikuPorts' Vulkan loader looks |
| Zink | `system/non-packaged/add-ons/opengl-zink` |

All of these are user add-ons, so the boot menu's "Disable user add-ons"
turns the whole stack off.

- **The driver** binds only to NVIDIA GPUs. It has been tested on Pascal;
  other generations that NVIDIA's 570 driver covers are untested on Haiku.
- **NVDEC** registers H.264 only when `/dev/nvidiactl` exists. Haiku uses one
  decoder per format, and an add-on that claimed H.264 everywhere would stop
  H.264 playing on every machine without an NVIDIA card.
- **Zink** is linked into `add-ons/opengl` by the image's boot script, and
  only where `/dev/nvidiactl` exists. The GL kit takes the first renderer it
  finds; Zink falls back to softpipe without a Vulkan device, and on such a
  machine HaikuPorts' llvmpipe renderer is faster.
- **NVK** is harmless without NVIDIA hardware: the Vulkan loader finds no
  device for it.
- **Summit's private Mesa** reaches the GPU through its own zink and NVK. On
  other machines it uses llvmpipe.

## Untested

CI cannot test any of this on hardware: QEMU has no NVIDIA GPU. The smoke
test shows only that the image boots with the driver present (`nvidia_rm:
module_init`, and NVKMS loads). Check the cross-built NVK and Zink on the
X399 with `docs/x399-workstation/tools/check-workstation.sh`. They are built
differently from the workstation's native builds:
- NVK is built without LLVM on the target;
- Rust's std comes from `-Zbuild-std`;
- Zink's fallback is softpipe.

## AMD: amdgpu_drm

AMD GPUs and APUs run on **amdgpu_drm**: Linux 6.18's amdgpu driver with the
DRM core, TTM, the GPU scheduler and Display Core, built as a Haiku kernel
driver over a Linux compatibility layer. It replaced the native WX 5100
driver (`amdgpu`) and its `amduvd` decoder, which left the Haiku tree on
2026-10-13. Haiku's `docs/x399-workstation/AMDGPU-DRM.md` has the details.

| Part | What it does | Source |
|---|---|---|
| `amdgpu_drm` package | the kernel driver: `/dev/graphics/amdgpu_drm_<n>` for app_server, `/dev/dri/card<n>` and `renderD<n>` for libdrm | jmgasper/linux-drm `airos-6.18.52` (Linux 6.18.52's DRM and amdgpu, `haiku/` the compatibility layer and driver), packaged by its `haiku/tools/package.sh` |
| `amdgpu_firmwares` package | the firmware the driver loads, `data/firmware/amdgpu` (699 files: Southern Islands to RDNA 4, the APUs) | jmgasper/airos-firmware `amdgpu/`: linux-firmware 20260916 (`ab23307c`), unchanged |
| `amdgpu_kms.accelerant` | app_server's side: modes, several monitors, the cursor, vertical sync | haiku `src/add-ons/accelerants/amdgpu_kms`, in `haiku.hpkg` |

`deps/build-amdgpu.sh` builds the driver against the kernel of the x86_64
SDK's Haiku build and makes both packages. Every x86_64 image build runs it
(a minute and a quarter from scratch; the objects are kept while the pin is),
so the driver package always requires the image's own `haiku` package. The
image puts both packages in `system/packages`; its `manifest.json` lists
them, and `amdgpu-sources.txt` the commits they came from.

- **Which GPUs:** the driver binds to AMD display controllers. Southern and
  Sea Islands GPUs (Radeon HD 7000, R7/R9 200) stay with `radeon_hd`
  unless asked for. Only the X399's WX 5100 (Polaris 10) has been tried;
  APUs, laptop panels (eDP) and backlight control are untested.
- **A start that fails:** the driver keeps the marker
  `~/config/settings/kernel/drivers/amdgpu_drm.starting` from the start
  until the GPU has run for 30 seconds. A boot that finds it (the previous
  one went down while the GPU started) leaves the GPU to the framebuffer
  driver until it is deleted. This needs a writable boot volume (a USB
  stick or an installation, not a CD). By hand: the boot menu's safe mode
  options, "Disable system components", then
  `add-ons/kernel/drivers/bin/amdgpu_drm`.
- **Not in the image yet:** the GPU user land (libdrm, libva, Mesa's
  radeonsi, RADV and VA driver, the `amdgpu_va` media add-on). Without it
  the display runs on the GPU, while OpenGL is llvmpipe and video decoding
  is software.

QEMU has no AMD GPU either: the smoke test shows only that the image boots
with the packages installed.
